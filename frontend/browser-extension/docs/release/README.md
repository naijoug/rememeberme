# Chrome release preparation

## First-lookup update (0.1.3, 2026-10-25)

Current packaging includes bounded automatic translation recovery after an
initial network failure. The first attempt has five seconds and both attempts
share nineteen seconds; vocabulary mutations are never retried. Magpie's low
reasoning and eight-second budget reserve room for MyMemory fallback.

snapshots. The backend now uses Magpie; installed 0.1.1 clients need updating.
The new ZIP passed disposable Chrome selection, source rendering, storage,
export/import and restart checks. Historical records below apply to their
original artifacts, not this ZIP. See [deployment and acceptance](../../../../backend/docs/verification/2026-10-24-magpie.md).

Set `REMEMBERME_ACCEPTANCE_DIR` when running `scripts/release-smoke.cjs` to save
new evidence separately from historical release screenshots.


Target: Chrome Web Store **0.1.1**. Publisher **naijoug**; support [GitHub Issues](https://github.com/naijoug/rememeberme/issues). This release includes local vocabulary and automatic server lookup; account login/synchronization is disabled until its hosted flow is accepted. Addresses are internal configuration. No store submission or approval is implied.

## Reproduce the Chrome candidate

Use Node **22.22.3** from `.nvmrc`, in `frontend/browser-extension/`:

```sh
nvm use
npm ci
npm audit
npm test
npm run compile
npm run zip
```

The `zip` command builds only in `.output/release-staging/chrome-mv3`, then extracts and verifies the archive before reporting success. It leaves the prior `.output/chrome-mv3` and active `.output/chrome-mv3-feedback` untouched.

Chrome output: `.output/remember-me-0.1.1-chrome.zip`. Upload only that production ZIP. Never upload repository configuration, secrets, a feedback build or a developer profile. The WXT upgrade preserves TypeScript strict mode with the prior unchecked-index behavior explicitly configured; it does not claim newly enabled unchecked-index enforcement. The production manifest requests `storage` and `contextMenus`; identity/alarms are absent. WXT's metadata importer receives Vue/CSS stubs only in its inline metadata environment; normal builds use real UI modules.

## Formal ZIP browser acceptance

`scripts/release-smoke.cjs` extracts the generated Chrome ZIP and loads those exact files in a fresh, disposable Chrome for Testing profile. It never attaches to the user's browser or real vocabulary. Its test-owned DevTools connection reads the actual closed shadow DOM without modifying production encapsulation.

The script exercises live word-only lookup, packaged English, absent API/login controls, intentional records, count reset/history retention, deletion confirmation, export/import, invalid JSON rejection and real process-restart persistence. It records actual screenshots and results; a failure does not become release evidence. The historical 0.1.0 native toolbar/right-click run is recorded in `assets/native-acceptance.json`. The 0.1.1 upgrade test additionally opens the real browser action popup offline using Chrome’s action API; its result records that separately from a manual menu click. The driver uses only its disposable profile and asserts exactly one word/count/history after completion.

With an already installed Playwright/Chromium runtime:

```sh
REMEMBERME_PLAYWRIGHT_PATH=/absolute/path/to/playwright node scripts/release-smoke.cjs
```

Run after `npm run zip`. Playwright is intentionally not a production dependency. Live provider/network results are separate from the mock unit suite.

Firefox packaging remains a separate release target. A successful build is not AMO acceptance. Its add-on identity, transmission/consent declarations, source archive and installed browser behavior need a dedicated verification. The current candidate is Chrome-only.

## Existing vocabulary

Legacy JSON count/history compatibility is retained. Reset preserves history. Import adds counts and history; import each backup once. Different extension identities have separate storage: export from the old installation and import once into the new one, verifying fixtures before retiring an old copy. Backups contain full URLs and sentences. Never replace profile files or use real vocabulary as test data.

## 0.1.1 popup recovery release

- A stalled read from the extension background stops loading after ten seconds and shows a retryable error. No writes time out or retry automatically.
- Release packaging uses a separate staging directory and verifies every linked popup/background/content script, transitive code import, stylesheet and image asset in the extracted ZIP. Missing files or development/temporary dependencies fail the command. A SHA-256 inventory accompanies the archive.
- `scripts/release-upgrade.cjs` loads the accepted 0.1.0 ZIP and the new ZIP at one test-owned install path/profile. It verifies unchanged identity/local data, repeated offline popup loads, a controlled stalled read, recovery, process restart and the actual Chrome action popup. Run with `REMEMBERME_PREVIOUS_ZIP=/absolute/path/to/accepted/remember-me-0.1.0-chrome.zip` and the Playwright variable shown above.
- Local feedback recovery helpers remain development tooling. The production ZIP bundles its own popup and has no localhost dependency. `local:start`/toolchain checks fix the development installation independently.
- Updating a manually unpacked installation requires a completed replacement in its original directory while it is not running, then reloading that same entry. Do not point Chrome at the disposable release-staging directory, which a later package build may recreate. Do not uninstall or repeatedly import a backup. Store distribution uses the same signed item; that external delivery is not simulated here.

Data processing is unchanged from the published 0.1.0 privacy policy, which also describes 0.1.1. Service addresses remain internal. A damaged/deleted installation directory cannot be made universally immune to ERR_FILE_NOT_FOUND; this release gates complete packages and prevents its own packaging process from clearing an active directory.
